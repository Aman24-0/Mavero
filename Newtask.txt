3. CRITICAL ROOT-CAUSE FIX — SESSION REGISTRATION
==============================================================

Current implementation uses a fire-and-forget pattern similar to:

    void registerCurrentSession(...).catch(...)

inside hooks.server.ts.

This is NOT acceptable for production session registration.

A session must not depend on an un-awaited background promise to become visible in the device registry.

Fix this.

The authenticated request must reliably register/heartbeat its session before the request lifecycle can finish, BUT:

- do not add significant latency to every request
- do not perform unnecessary DB writes
- do not break serverless execution
- do not block authentication indefinitely
- use a short timeout where appropriate
- use the existing heartbeat throttling/RPC design
- preserve failure-safe behaviour

The correct architecture should be:

Authenticated request
    ↓
derive user.id from Supabase auth
    ↓
derive session_id from JWT
    ↓
derive stable device_id from cookie
    ↓
parse device metadata
    ↓
register/heartbeat current session
    ↓
continue request

Use the existing register_device_session RPC where appropriate.

DO NOT resurrect revoked sessions.

If a registry row exists and is revoked:
    never reactivate it.

If the current Supabase session_id is new:
    create a new registry row.

If the same session_id already exists:
    update last_seen_at according to heartbeat policy.

If the same physical browser/device has a NEW Supabase session_id:
    this is a NEW session and must be represented correctly.
